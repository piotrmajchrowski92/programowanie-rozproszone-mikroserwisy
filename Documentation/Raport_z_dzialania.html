System zgłoszeń w architekturze mikroserwisowej

C# / ASP.NET Core 8 / Visual Studio / JWT / SQLite / Razor Pages

1. Cel i zakres

System składa się z trzech mikroserwisów, centralnego API Gateway i klienta webowego. Użytkownik może utworzyć konto, zalogować się, zarządzać swoimi zgłoszeniami i przeglądać historię działań.

2. Architektura

Przeglądarka → WebClient :5200 → ApiGateway :5100
                              ├→ AuthService :5101 → auth.db
                              ├→ TicketService :5102 → tickets.db
                              └→ LogService :5103 → logs.db
AuthService/TicketService → Gateway /internal/logs → LogService

Shared jest biblioteką kontraktów i wspólnej infrastruktury. Serwisy nie odczytują baz pozostałych serwisów.

3. Składniki

4. Uruchomienie w Visual Studio

  1. Zainstaluj Visual Studio 2022 z aktualizacjami, komponent ASP.NET i tworzenie aplikacji internetowych oraz SDK .NET 8.
  2. Otwórz MicroservicesAssignment.sln i przywróć pakiety NuGet.
  3. W konfiguracji wielu projektów startowych ustaw Start: LogService, AuthService, TicketService, ApiGateway i WebClient. Shared nie jest uruchamiany.
  4. Uruchom F5 i otwórz http://127.0.0.1:5200.

Bazy SQLite tworzą się automatycznie w katalogu Data każdego mikroserwisu. Nie jest potrzebny SQL Server.

6. Bezpieczeństwo i ograniczenia

  • Hasła nie są przechowywane jawnie. JWT zawiera sub, email, jti oraz czas ważności.
  • Gateway i mikroserwisy niezależnie sprawdzają podpis, wystawcę, odbiorcę i ważność JWT. Właściciel zgłoszeń pochodzi z sub.
  • SQL używa parametrów. Razor koduje wyświetlany tekst. Formularze Razor Pages mają ochronę anty-CSRF.
  • Klucze w appsettings.json są demonstracyjne. HTTP i nasłuch na loopback służą testom lokalnym.
  • Zapisy logów są best-effort; awaria LogService nie cofa CRUD. Nie ma outbox, refresh tokenów, blacklisty JWT ani ról administratora.

7. Weryfikacja

Skrypt scripts/Smoke-Test.ps1 sprawdza API, pełny CRUD, błędne hasło, duplikat e-mail, brak lub uszkodzenie JWT, walidację, izolację danych i komplet logów. Demonstracja interfejsu jest oddzielnym scenariuszem weryfikacji.

8.1. Ekran początkowy

Klient udostępnia formularze rejestracji i logowania. Bez logowania panel CRUD nie jest wyświetlany.

8.2. Rejestracja użytkownika

AuthService zapisuje użytkownika i skrót hasła we własnej bazie. Działanie REGISTER trafia do LogService przez Gateway.

8.3. Logowanie i sesja

AuthService wydaje JWT. WebClient przechowuje token w sesji po stronie serwera i dodaje nagłówek Bearer do kolejnych wywołań API.

8.4. Dodanie i odczyt zgłoszenia

POST /api/tickets dodaje rekord, a GET /api/tickets odświeża listę. Właściciel pochodzi z podpisanego JWT, nie z danych formularza.

8.5. Aktualizacja zgłoszenia

PUT /api/tickets/{id} zmienia tytuł i status. UPDATE jest zapisywane w dzienniku zdarzeń.

8.6. Weryfikacja JWT

GET /api/auth/validate wymaga poprawnego podpisu, wystawcy, odbiorcy i czasu ważności tokenu. Weryfikacja działa również przy każdym autoryzowanym CRUD.

8.7. Usunięcie i podgląd logów

DELETE /api/tickets/{id} usuwa rekord. Dziennik nadal zawiera REGISTER, LOGIN, CREATE, READ, READ_LIST, UPDATE i DELETE.

8.8. Wylogowanie

Usunięto token z sesji klienta. Nie zastosowano listy unieważnionych JWT; wydany wcześniej token wygasa zgodnie z exp.
